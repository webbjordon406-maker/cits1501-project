# AI Log

This file documents significant AI use throughout the project. For each use it records what I asked for, what the AI produced, and how I checked, changed or rejected its output.

All information about the Nyoongar seasons and the calendar overview came from my own research of the Bureau of Meteorology's Nyoongar calendar. No cultural, language or historical content was generated by AI.

# Use 1 – Grouping the data into seasons
Prompt: "Write me code to group the data into six categories based on their date. 1. Birak = December and January 2. Bunuru = February and March 3. Djeran = April and May 4. Makuru = June and July 5. Djilba = August and September 6. Kambarang = October and November."

AI output: The `MONTH_TO_SEASON` dictionary and the code that gives each day a season, now in `assign_seasons()` in `data.py`.

My checks: I supplied the month ranges myself from the BoM calendar rather than letting the AI choose them. Manually confirmed that each season got the right number of days (Birak 62 = 31 + 31, Bunuru 59 = 28 + 31).

# Use 2 – Organising the data code into functions
AI output: The data loading and season assignment were reorganised into functions. These run in a logical order, check that the data file and expected columns exist, and can be tested for invalid inputs and edge cases.

My checks: I confirmed the dates are read in Australian day/month/year order. 

# Use 3 – Season analysis
AI output: Code to analyse the data per season: `season_summary` (averages and totals), `count_extreme_days` (days above or below a threshold) and `season_detail` (statistics and event counts for one season) in `analysis.py`.

My checks: I checked a few random results by hand against the CSV

# Use 4 – Weather events chart
Prompt: "Write code that makes a bar chart of the 6 seasons and their season detail. Have the x-axis be the season, y-axis be the count and have one bar per event, using appropriate colours."

AI output: A grouped bar chart of the weather event counts per season, now drawn with Plotly on the home page.

# Use 5 – App structure
AI output: The structure and code for the web app: `app.py` (the Flask routes and JSON API) and `index.html`, `season.html` and `error.html` (what is shown on each screen).

Note: All information about the seasons and the overview of the calendar was gathered through my own research and is stored in `seasons.json`. AI was only used to turn this research into usable code, not to write any of it.

# Use 6 – Visual style
AI output: AI helped improve the visual style of the home page. I described the design choices and layout I wanted, and the AI provided the code to achieve them.

AI was then used to apply the same style to each season page. This included creating `style.css` so that all pages share one consistent style, which also simplified each HTML file.

# Use 7 – Removing unnecessary features
I noticed that the code from Uses 4–6 included functionality the app didn't need. I went through it myself and removed the features I judged unnecessary, which broke the code. AI was then used to repair it, giving a working and simpler version of the app.

This also included removing `print()` and `show()` lines that I had used to check the data analysis code.

Outcome: This was a case of rejecting part of the AI's output. I decided what to keep, and the AI only fixed the code after my changes.

# Use 8 – Automated tests
AI output: Help writing the automated tests in `test_data.py`, `test_analysis.py` and `test_app.py`, following the structure from Lab 09. I also asked the AI to suggest edge cases I might have missed.

My checks:
- I checked the expected numbers in the tests by hand against the CSV.
- Two of the edge-case tests failed and exposed real bugs. `season_detail` rejected a lowercase season name such as "makuru", and `count_extreme_days` crashed with a `TypeError` when the threshold was text instead of a number. I fixed both in `analysis.py` rather than changing the tests, and all 15 tests then passed.

# Use 10 – The "Match a day" feature
Prompt: I asked the AI to design a tool that lets users enter a temperature and rainfall amount and find out which season it is most like, based on the dataset. This gives the app meaningful user interaction and a good place to test edge cases and invalid inputs.

AI output:
- `closest_season()` in `analysis.py`. It loops over the six seasons (a linear search), measures how far the user's day is from each season's average day, and keeps the closest.
- `to_number()`, which checks the inputs.
- The `/api/match` route.
- The `match.html` page.
- An error message for invalid inputs, so the app shows what to fix instead of crashing.

My checks:
- I compared the results with the season averages to make sure they made sense. A 38°C dry day matches Birak (average 31.2°C, 0.3 mm), and a 16°C day with 20 mm of rain matches Makuru (average 19.4°C, 2.9 mm).
- 13 new tests cover the algorithm, the input limits (0–50°C and 0–300 mm) and invalid inputs such as blanks, text, negative rain and a 60°C day. All 28 tests pass.
